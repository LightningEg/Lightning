# Update survival and mixed phone/PC versions

Date: 2026-11-27
Reviewed commit: e1426e49 (v2.3.3), compared with v2.3.1 and v2.3.2
Code: r42
Pillar: protect

## Findings

1. Windows can undo its own live update. The staged helper records “launched” before starting the new EXE. The child runs startup repair before it starts the profile server. With no success marker, repair interprets that live attempt as abandoned. Exercising UpdateController.startup on temporary folders in this state restored the old folder and marked the attempt failed on Linux. Windows file locks can instead prevent the rename. Let the helper own recovery during an active attempt. Stage and verify the incoming folder before moving the original and keep a recovery entry point available across power loss. [Startup](../../../lightning/desktop/app.py), [controller](../../../lightning/desktop/update_controller.py), [swap](../../../lightning/desktop/update_helper.py).
2. The helper accepts a marker named only for the target version. A leftover marker can satisfy a later attempt. The middleware also marks success on a GET before the downstream response renders. Use a fresh attempt identifier, acknowledge after a successful chooser response and keep separate evidence of profile migration. An executable rollback after a schema change needs an explicit data recovery path. [Middleware](../../../lightning/runtime/app.py), [helper](../../../lightning/desktop/update_helper.py).
3. Journal sync refuses both directions for the requested pair even with an empty queue. The two earlier releases use schema 87 and v2.3.3 uses 95. The app version is descriptive. Protocol, effects, ledger schema, catalog and pending commands determine compatibility. The compatibility gate directed the older device to update in both orientations. For future patch lines, maintain one baseline for pairing and ordinary edits, and defer newer operations until both ends support them. Existing binaries require either an implemented bridge or a coordinated transition. [Compatibility](../../../lightning/sync/journal/compatibility.py), [migrations](../../../lightning/database/migrations).
4. Fresh enrollment fails earlier when the newer home advertises two-digit matching. The old peer rejects that method. A newer joining device understands the older offer. Provide a compatible authenticated pairing method in both orientations. [Runtime offer](../../../lightning/runtime/journal_pairing.py), [protocol](../../../lightning/sync/journal/pairing.py).
5. Borrowing, returning and checkpoint repair carry the database itself. They verify schema and identity. A shared product version prefix cannot make an older executable understand schema 95. Keep native checkpoints exact and implement a verified common representation if mixed-version full-ledger transfers are required. Preserve pending edits across reconnect and re-enrollment. [Copy validation](../../../lightning/sync/copies.py), [borrow and return](../../../lightning/sync/service.py), [checkpoints](../../../lightning/sync/journal/snapshots.py), [upgrade barrier](../../../lightning/sync/journal/upgrades.py).
6. Same-channel Android updates preserve the private storage identity when Android accepts the replacement. The earlier test-ID change left the book inside the old installation. GitHub and Play still have distinct IDs. Deleting the original clears its private data. Outside backups require prior setup. External profile imports are available, but a journal import opens as a review copy. The PC-to-replacement-phone recovery flow remains tracked separately. [Identity tests](../../../tests/test_phone_identity_frozen.py), [recovery item](../BT-2AI-phone-data-survives-updates.md).
7. CI verifies matched artifacts. A clean launch and one-revision tests omit the failing Windows parent/child sequence and mixed-tag behavior. Gate releases on both update orders, existing and new pairings, offline edits, borrow/return and interrupted recovery. Assert ledger totals, pending-edit identity, paired identity and that each edit is committed exactly once. [Release workflow](../../../.github/workflows/desktop-probe.yml), [helper tests](../../../tests/test_desktop_update_helper.py).

## Evidence and limits

The encrypted v2.3.1 round-trip fixture migrated with v2.3.3 from schema 87 to 95. Counts stayed at 74 transactions and 90 ledger entries, SQLite integrity returned ok and there were zero foreign-key violations. Eight focused test modules passed (89 tests). Controlled calls exercised the journal compatibility gate and the updater startup path. Native Windows ZIP replacement, Android package replacement and two-device communication were outside this Linux run. The results establish software failure paths and do not identify which occurred on a particular device.

## Desktop shortcut follow-up, 2026-11-27

The owner reports that an existing desktop shortcut still opens the old release after a PC update. Explorer shows Lightning and Lightning.previous alongside each other. The screenshot establishes both folders exist. It does not show the shortcut target or either executable's version.

The helper moves the original executable into Lightning.previous before placing the new copy at the original path. A Windows shell link can track a moved target. Cleanup permits the rollback folder to remain when removal fails. A rollback that restores the old binary at the usual path is another possible explanation. The helper's success log also says the folder was deleted even when cleanup deferred deletion. [Swap and cleanup](../../../lightning/desktop/update_helper.py).

Verify by creating a desktop shortcut to the old released executable on Windows before updating. Open that same shortcut after success, after a restart with cleanup deferred, and after rollback. Record the running executable path and version in each case. A successful update must launch the new build from the canonical installation through the existing shortcut. The updater must retain only the intended recovery copy, report its cleanup accurately, and avoid rewriting unrelated user shortcuts.
