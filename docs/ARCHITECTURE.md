# Architecture

Last reviewed 2026-10-14 · app 1.1.0b1 · schema 0053

How Lightning is built and calculated: stack, module boundaries, data model and every calculation contract. History lives in [CHANGELOG.md](../CHANGELOG.md), the product story in [Project Overview](PROJECT_OVERVIEW.md), term definitions in the [Glossary](GLOSSARY.md), the visual system in the [Brand guideline](../guideline/), open items and unbuilt designs in [issues/](../issues/INDEX.md). Where the code or a test states a rule better, this file names it instead of copying it.

Lightning is a local-first, single-user modular monolith: one Python process, one SQLite database, a server-rendered browser UI. Correctness first, then clear ownership of data, then new asset types without duplicated transaction logic.

## Stack and local operation

| Area | Choice |
|---|---|
| Runtime | Python 3.11+, FastAPI, Uvicorn |
| UI | Jinja2 server-rendered HTML, vanilla JS/CSS, no frontend build |
| Persistence | One SQLite file, ordered SQL migrations, local backups |
| Precision | `Decimal` in Python, scaled integers (`_e6`) in SQLite; no binary floats in financial logic |
| Quality | pytest and `import-linter` (`[tool.importlinter]` in `pyproject.toml`, run by `tests/test_architecture.py`) |
| Network | Local server on `127.0.0.1` only |

Legacy mode: `./run.sh` or `python -m lightning` opens `http://127.0.0.1:8765` (plaintext `data/lightning.db`). Startup takes a backup, runs migrations and processes due valuation checkpoints. `python -m lightning --demo` opens the sample household (`lightning/demo.py`) in `data/demo.db` on port 8766, rebuilt on every start; `--sample` does the same with Mohab's 2026 and pins today to its last row (2026-10-02, `lightning/samples/__init__.py`) unless `LIGHTNING_TODAY` is set. The main product runs as encrypted profiles (see Desktop app).

## Three layers: ledger, plan, report

These describe what data *is*, not which package may import which.

| Layer | Holds | Modules | Moves money? |
|---|---|---|---|
| **Ledger** (real money) | Accounts, posted transactions and ledger lines, prices and valuations, custody (held for others) | `accounts`, `transactions`, `assets`, trades in `investments`, `money_from_others`, `physical_items` | Yes. Only `TransactionService` writes postings. |
| **Plan** (what-if) | Budget rules and carryover, reserves, planned items and payments, sale factors, the cash forecast | `budgeting`, `reserves`, `planning` | No. "Record and mark paid" posts an ordinary transaction through `TransactionService`; the plan then links to it. |
| **Report** | Nothing of its own: figures computed on read | `reporting`, `planning.position` (`PositionService`), `investments.report`, `integrity`, `ui` | No. |

- **Real money is only what the ledger says.** A budget, reserve, scheduled bill or forecast never appears in a ledger figure.
- **A plan figure is labelled as one.** What you owe, reserves, planned amounts, safe to spend, the forecast and every "(estimate)" come from the plan, alone or with the ledger.
- **Each figure has one name, one formula, one function**, in `lightning/core/figures.py` with its layer. The Glossary's figure tables are generated from it (`python -m lightning.core.figures`); `tests/test_figures.py` checks they match and every named function exists.
- **Routes never compute figures.** A screen calls the function the registry names.

## Runtime and dependency direction

```
ui/                   FastAPI routes, Jinja templates, small vanilla JS/CSS; no SQL, no calculations
workflows/            transactional use-cases spanning modules
planning/             recurring items, loans, what you owe, cash forecast (read-only)
domain services/      accounts, assets, categories, transactions, investments, deposits, budgeting
reporting/            read-only queries and derived views
database/             SQLite, migrations, seed, backup, settings, audit
core/                 dates, money, identifiers, posting rules; no app dependencies
```

`bootstrap.py` is the composition root. Cross-module operations call public services, never another module's repository. `import-linter` and tests enforce this. Only `TransactionService` writes postings; other modules build validated postings and ask it.

**Price packs and live prices.** Packs (`lightning/market`): checked pack format, registry, delta download and import. **Cash at hand** is a form subtype of the cash account type (`accounts.cash_at_hand`); its balance stays in the Physical Cash child under Liquid Cash.

## One main ledger; one linked valuation ledger

The main ledger is the source of truth. Registers, budgets, net worth, positions and analysis are views over it, never competing stores.

```
transactions (documents) ──1:n──▶ ledger_entries (account + asset effects)
                                           ▲
reevaluation_entries ──many:one── reevaluation period ──1:1 per account──▶ VAL journal in main ledger
```

The reevaluation ledger keeps per-asset, per-account month-end units, price, value, return and missing-price state, and links each row to one system `VAL` journal per account and checkpoint. It never copies ordinary transactions. Sale dates force a checkpoint at the sale price; month-end checkpoints fill on startup. A missing historical price leaves the checkpoint pending for user input; cost is never silently used as a quote. Certificates keep their purchase price as principal until a manual dated valuation replaces it, so they ask for no monthly quote; a CD portfolio's `VAL` journal has one zero-quantity noncash line per asset and owner. Manual `VAL` postings to CD portfolios are prohibited.

| Activity | Main-ledger effect |
|---|---|
| Expense 450 | Account cash −450, `OUTFLOW`, category by activity |
| CIB → THNDR transfer | CIB −10,000, THNDR +10,000, both `INTERNAL` |
| Investment buy | Brokerage cash down; units and cost up; net effect internal |
| Money held for Dad | Cash enters the named account; custody attribution reduces the owned share |
| Month-end return | Per-holding detail in reevaluation ledger; one account-level `VAL` journal |

**Posting invariants.** Internal lines net to zero; external inflows/outflows have a category; a sale cannot take an owner's position below zero; voided entries stay auditable but count nowhere. `ledger_entries.owner_id` null means user-owned, otherwise that Counterparty owns the line; a transaction's owner is copied to its lines, and dated cash and holdings are checked per account, asset and owner. A zero-sum `ADJ` (description prefix `Ownership:`) moves cash between the user and one saved person inside an account; when another person paid an expense it holds a user-owned categorised outflow and an equal payer-owned inflow, so gross cash is unchanged, owned cash falls, and the expense line still matches budget, reserve and planned payments.

**Cash never goes below zero by your own entry.** A manual money in/out or transfer (`_refuse_cash_below_zero`) is refused when it leaves a wallet or bank account's whole cash, whoever owns it, lower than before and below zero on any day from the account's opening date; an edit that does not lower the minimum (a note, a category) passes. Imports, system postings and conversions are not checked; a `PHYSICAL_ASSET` account refuses money in and out. The Integrity page lists any account below zero (*No cash account is below zero*).

**Brokerage buys** must use cash of the same owner in the same brokerage account on the trade date. **CD purchases**: a `DEPOSIT` account is a bank-specific portfolio (Institution field) that cannot hold cash; each certificate is a separate non-cash `DEPOSIT.CD` asset; a `BUY` links it to the portfolio and debits the bank/cash account the user selects. Membership comes from the explicit account link, never from matching institution text.

### Physical gold item contract

- An item is one named thing in one `PHYSICAL_ASSET` account; quantity counts pieces; no ticker or ISIN. `net_gold_grams_per_piece` is the gold-bearing alloy per piece, stones excluded; the karat is its fineness, not a second multiplier.
- `acquisition_cost` is the total paid for the current pieces (workmanship, stones, fees); historical, never moves with prices.
- A shared reference asset gives price per gram per karat in account currency (`GLD:18K`) and must match the item's karat. Estimated metal value = `piece_count × net_gold_grams_per_piece × dated_price_per_gram` (do not multiply by `karat/24`); fine-gold exposure is reported separately as `piece_count × grams × karat/24`.
- Stones and workmanship have no resale value in the estimate. A manual dated total-item valuation overrides the reference estimate from its date. Labels: `Manual`; reference source and price date; `At cost`; or unavailable.
- Metadata, weight and karat edits post nothing and never change history or cost (the audit log keeps before/after). Purchases and sales are normal `BUY`/`SEL` with pieces and grams kept apart from cash; pieces cannot go below zero; a purchase is not income, expense or owned-wealth change.
- Values enter the owning account and the Gold allocation path exactly once; gram-based gold positions are untouched.
- `physical_items.worn` (default 0, migration 0054) marks gold the user wears; only Zakat reads it.

## Data ownership and derived values

- **Where:** `accounts` (cash, bank, CD portfolio, brokerage, physical-asset location, other). **What:** `financial_assets`, `asset_classes`. **Why:** `categories` (L1 Personal, Work or Investment; L2 broad; L3 unused). **Who:** `counterparties`, copied from the transaction's `Whom` to its lines.
- Holdings, cash balances, budget actuals, ownership shares, gains and net worth are calculated from posted ledger effects, owner IDs and dated prices.
- Whole-asset estimates for Other asset accounts are kept by effective date (`other_asset_valuations`); they replace that account's cash-like value in as-of reports and post nothing.
- IDs are internal keys; stable refs identify transactions; readable codes identify master records for imports and search. Screens show names. Source CSV spellings are kept during review; counterparty matches are suggestions, never silent merges.
- **Integrity checks** (read-only, `lightning/integrity.py`): gross account values against asset-class reports; `owned net worth + held for others = gross`, overall and per account; categorised outflows against spending and budget actuals; reserves against owned liquid cash; the month-to-date net-worth bridge. Missing valuations make a comparison incomplete, never green. They never adjust entries.

**Default category for a counterparty** (register and CSV import): the counterparty's own category, else its *usual category* (`TransactionService.usual_categories`): the same category in at least 3 of its last 5 categorised transactions, or in every one while it has 2 to 4, counting only the 180 days before its newest (as Actual Budget). With no habit the field stays empty. **A rule comes first** (`RuleService.outcome`, Glossary › Rule): in import review it sets the category, adds its tags to the notes and, for money out kept in the rule's category, splits the expense (`update_expense_split`). The register fills a category as you type only from rules on the name alone; a rule needing amount, notes or account decides on saving (`register.category_when_empty`, also the phone's entry sheet). Applying a rule to the past refiles only single-category, owned money-in/out rows it decides among all rules (never system categories), with old categories kept for one undo (setting `rules_apply_undo`); splits and tags never change the past.

## Position and reporting contract

### Investment report contract

Holdings-table gain includes unrealized gain, realized sales and income; its plain return uses all original purchases, including sold units, as denominator (`Position.owned_result`, owner-specific invested-cost pools). The holding, group and total rows include certificate interest paid into a bank. Price/FX breakdowns remain price gain only. The income section names dividends and interest explicitly.

Uses posted, non-void main-ledger entries by transaction date, scoped to `owner_id IS NULL`, with cost lots keyed by owner, account and asset. An opening (`OPN`) holding is a baseline, never new money.

- **Boundary** (owner decisions 2026-10-04): the portfolio includes investment holdings. Brokerage cash is not part of any portfolio figure (it counts in Cash you own). A balance kept in a physical-asset or Other account, or left as cash in a deposit account, is that asset's value, a holding with `price_source` `BALANCE`. **Everything that is not cash sits under one roof**: certificates, stocks, funds, gold and other assets all count in Holdings value, which is Portfolio value. *Deposits* is a part of it, never added beside it. What you own = Cash you own + Holdings value + Other you own; If you sold today = Free cash + Holdings after sale.
- Transfers and trades inside investment accounts net internally; direct physical purchases/sales count only their holding change. Dividends are distributions, not contributions. Checkpoint rows (`return_base_e6`) and `VAL` journals are reconciliation data, excluded from return.
- **Interval:** new money is the positive posted change across the boundary, withdrawals the absolute negative change, money added their difference. Gain from sales = net sale proceeds less average cost removed (basis per owner/account/asset, fees included). Distributions use cash actually posted. Price change on what you hold = end balance less the balance just before. Net gain or loss adds gain from sales, price change, distributions and separately identified FX/cost effects once; no balancing "other return". Missing prices or ownership make it unavailable.
- **As of a date:** cost of holdings = remaining basis; holdings value = units × a dated confirmed valuation; unrealized gain = value less basis. An asset with no typed or trade price yet is valued at remaining cost and listed in the report's `at_cost` notices; a missing price after that makes Net gain unavailable. Dividend attribution is stored in `investment_dividend_assets`. YTD is labelled Calendar 2026 (no fiscal-year setting).
- **Investment return:** holdings value less remaining cost, plus gains from sales and dividends. Certificate interest lands on a bank/cash account as Investment › Interest; when its payer is a CD portfolio's Institution (any case) it is that portfolio's certificates' interest, split by cost held that day (`ReportingService.certificate_interest`), in Dividends and interest, Net gain and XIRR (owner decision 2026-10-06). Portfolio and management XIRR must not be assumed owned-only until historical custody cash flows are verified.
- **Events** (`InvestmentService.dividend/broker_fee/broker_interest/move_units`): a dividend is net by default; an optional *Tax was taken* posts the gross as Dividends and the tax as an outflow in the investment category Investment › Tax withheld (`EXP.INVEST.TAX`) in the same `DIV` transaction. Dividends and interest stay gross; **Net gain = realized + price change + dividends and interest − tax withheld − broker fees**, so Position, holding page and report use `net_dividends`. A broker fee (`EXP.INVEST.FEES`, Investment Fees) and tax are investment costs: left out of Money added and of household spending and budgets. Interest on broker cash is `EXP.INVEST.INTEREST`. Moving shares is a `TRF` with two INTERNAL unit lines at the source's average cost (your own units only, brokerage to brokerage, same currency): no cash, no gain, Net gain unchanged.
- **Price and FX apart** (`investments/report.py::foreign_gain_split`): for a holding priced in another currency, `price_part = (value − cost) in its currency × today's rate`, `fx_part = cost in its currency × today's rate − cost in the profile currency`; they add to its unrealized gain.
- **Portfolio reconciliation** (`investments/report.py::reconcile_portfolio`): closing value (holdings + investment cash) = opening value + Money added + Result + opening balances entered in the period − certificate interest paid to the bank + the **exchange-rate revaluation of investment cash** (its change in value less what the period's postings moved in; zero in the profile currency). That revaluation is not an investment result, so it is its own term, not inside Result; whatever is left shows as the notice "Portfolio reconciliation differs".
- **Views and lens** (`investments/views.py`, design 2026-10-15 §9): the holdings table is the same rows regrouped by class, account (a pocket under its broker), currency, market or security, so every view sums to Holdings value; By currency adds brokerage cash per currency (`investment_cash_by_currency`); `?lens=usd` divides every figure shown by the dated USD rate and stores nothing; the exchange-rate share of the gain is Σ `fx_part`.

### Shared figures and rules

- **Kept apart** (audit 2026-10-15): owned cash in brokerages, in another currency or in an account set apart (`accounts.spendable`, NULL = default by `Account.counts_as_spendable`) stays in Cash you own but leaves Free cash, Safe to spend and the payday pool; If you sold today adds it back. Three-decimal currencies (KWD, BHD, OMR, JOD) keep three places (`currencies.minor_units`).
- **Position figures** (What you own, Cash you own, Deposits, Holdings value, Reserves, Bills due, What you owe, Net worth, Free cash, Portfolio value, Holdings after sale, If you sold today) come from `PositionService.at(date)` in `lightning/planning/position.py`. Base values are read from reporting, reserves and planning; every other figure is a property composing them (`free_cash = cash_you_own − reserves − bills_due`). Routes and templates read the `Position`; they never re-add balances. Historical after-sale estimates use current sale factors; an unavailable reserve history makes Free cash and If you sold today unavailable.
- **Sale factors:** each asset class has a 0–100% factor (95% unset, `investments.domain.DEFAULT_SALE_FACTOR`). Holdings after sale = Σ holdings value × factor, deposits included (CDs follow their early-withdrawal terms). A scenario with current settings, not a quote or booked loss.
- **Average monthly income:** `BudgetService.income_average(month)` is the only income average: chosen income categories over the last 3 or 6 completed months that had income, or a manual amount. A recurring-income transaction explicitly linked to a scheduled payment counts in that payment's due month (cash-flow reports keep the bank date). Budget percentages, emergency-fund coverage and the forecast read it.
- **Average monthly spending:** `BudgetService.spending_average(month)`: household money out (investments and one-off categories left out) over the same window. `BudgetService.emergency_fund(month, set_aside)` counts the fund in months of income or spending (setting `emergency_fund_basis`, `spending` default; explicit saved income choices are preserved) against a six-month target.
- **One rule for Money in and Money out** (2026-10-04): `reporting.service.flow_of(effect, amount, category)`. A line with the income effect in a category with an income class is Money in; every other categorised line is spending, where a payment adds and a refund (a positive amount, whatever effect it was recorded with) takes away. Every adding path uses it on the same rows (cash flow, month trends, calendars, category and spending breakdowns, Budget, which also leaves investment categories out); `tests/test_one_money_rule.py` checks they agree. "Money in" on an expense category records a refund (`record_inflow` → `record_refund`).
- **Period flows:** posted external activity in the range. Internal transfers and investment purchases are not income or expense; custody is excluded from owned analysis.
- **XIRR** is an annualised money-weighted rate over dated investment cash flows and an ending value; since-inception XIRR is separate from a period's currency return, and a period XIRR needs an opening valuation. If inputs are inadequate show an unavailable reason, never 0%, and never invent quotes.
- **Overview and reports** share one date-range parser (`ui/periods.py`; Birdview was folded into the Overview on 2026-09-30, `/birdview` redirects, Expense analysis keeps `/birdview/expenses`). Flows use the selected interval; position cards are valued at the period end, never after today (feedback ticket 80, 2026-10-14), so they agree with the Net worth chart beside them. Plan to invest shows only when that is today. In a month, Where money in went sits beside the six months ending with it (`dashboard.PAIR_XS` narrows the columns). Month by month is net cash flow by month as a calendar; the daily expenses calendar is on Spending only. Expense analysis uses daily calendars up to 92 days, monthly beyond. Asset-class weights divide by owned investment value, excluding cash and custody.

### Figures layer and speed

**Figures layer** (2026-10-04). Every screen number is a registry figure computed by the function the registry names; `ui/visuals.py` and templates only draw. To add one: a registry row in `lightning/core/figures.py` (name, meaning, formula, function), the function in a service, `python -m lightning.core.figures` to regenerate the Glossary, then draw it. `tests/test_figures_layer.py` guards it.

**No stored calculations table** (decided 2026-10-04). The registry plus the services it names are the one place that computes every figure. Stored daily figures were not built: a back-dated edit rewrites every later day, plan figures depend on today and settings, and a missed refresh shows wrong numbers silently. Revisit at about 4,000 transactions or any tab over 400 ms: [9A](../issues/9-later/9A-stored-month-end-figures.md).

**Request cache** (`lightning/core/memo.py`). `ui/web.py` wraps each request in `request_cache(container.db)`; a read decorated `@request_cached` runs once per distinct call per request. It lives one request, any write empties it, it is bypassed inside a transaction, and callers get copies. `tests/test_reporting_performance.py` caps SELECTs per tab and checks pages are byte-identical with and without it.

**Page speed** (2026-10-03, 2,239 transactions: Overview 507 to 163 ms, Budget › All time 4.6 s to 0.33 s). Fixes: the request cache; `cipher_memory_security` off (see Encryption); registers read one page of 50 (`ReportingService.register_page`; a search or category filter shows no running balance); bundled fonts. Open: routes are `async def` with synchronous database work.

### Zakat

An estimate by the common rule, never a ruling: the page says once that a scholar answers your own case (owner decision 2026-10-14). `lightning/zakat.py`, `ZakatService.assess(day)`, Python only; routes `lightning/ui/routes/zakat.py`; migration `0054_zakat.sql`.

- **Off until turned on** (owner, 2026-10-14): Settings › Your data › Zakat, *Show zakat* (`settings` key `zakat_enabled`, `ZakatService.enabled`). While off there is no Zakat tab, gear or search entry, `/zakat` and its settings redirect to Settings, Cash planning has no zakat line and gold pieces have no *I wear this piece* box; turning it off keeps its settings.
- **Built from the one position** (`PositionService.at`), never re-adding balances; *Held for others* is never in it. **Zakatable wealth** = Cash you own + Deposits (principal; unpaid estimated interest left out) + Gam'eya paid in + Shares and funds (latest price, full value, no sale factor) + Gold held as savings (physical pieces and gram gold at the gold price) + Gold you wear, only if `count_worn_gold` − Debts due now (Bills due) − Gam'eya instalments due now (unrecorded instalments dated by that day on a circle you owe, capped at what you owe it; before your turn an instalment is saving, not debt), both unless `deduct_debts_due` is off; never below zero. Other assets, property and vehicles are not counted. A line off by its setting is still listed, with a note.
- **Nisab** = 85 g × the price of a gram of 24K gold on the day (`ZakatService.gold_price_24k`: the 24K reference price, else the newest other gold reference ÷ its purity); with no gold price, the nisab the user typed (kept with its date). **Zakat due** = 2.5% of Zakatable wealth when it is at or above the Nisab, else 0. A missing valuation (`Position.unvalued`) or a missing nisab gives no estimate and says why, never zero. A silver nisab is not built.
- **Zakat day.** The user picks a date once (`zakat_settings.zakat_day`); the next is +354 days (`zakat_days`), so it moves about 11 days earlier each year. The page shows the Gregorian date and says it follows the lunar year; Hijri dates are not built. Nothing is shown as due on a day until one is picked.
- **Paid and Still to pay.** Zakat is paid as ordinary spending in the system category **Zakat** (`EXP.SYSTEM.ZAKAT`, pickable, counted in money out). **Paid this zakat year** = that category's money out after the previous zakat day, up to and including the next one; **Still to pay** = Zakat due − Paid, never below zero. The page's *Record payment* opens the first bank or wallet's entry sheet with the category set.
- **Settings** (`zakat_settings`, one row: `zakat_day`, `typed_nisab_e6` and its date, `count_worn_gold` 0, `deduct_debts_due` 1) sit behind the Zakat tab's gear, audited as `zakat_settings`. The tab is in Accounts, beside Held for others (four tabs fit the phone's two rows).
- **Cash planning** shows `ZakatService.forecast(day)`: the next zakat day and what is still to pay then at today's figures, as a labelled line under the forecast. It changes no balance and is not in the forecast months; it is absent until a zakat day is set.

## Cash planning contract

`lightning/planning/` owns planned items (`planned_items`) and payments (`planned_payments`). It reads the ledger, budget and reserves through services and never posts; recording a payment goes through `TransactionService`.

- **Dated scheduled cash check.** `planning/dated_cash.py` adds `CashForecast.dated` alongside the monthly free-cash forecast. It starts with owned cash quantities in wallet, bank and brokerage accounts (no securities or custody cash), applies outstanding scheduled payments and projected CD/gam’eya cash events by date, and reports the first negative day-end total and the first negative day-end balance in each funding account. Overdue bills count today; overdue income is excluded because its receipt date is unknown. Movements on the same date net together; no intraday ordering or automatic transfers are assumed. Account amounts stay in native currency; combined cash uses the as-of FX rate throughout. Missing FX makes the combined forecast unavailable while native account checks still work. Items without a liquid funding account use profile currency in the combined total and are flagged as unassigned, never assigned to an account by guesswork. This check includes reserved cash and excludes flexible budget spending and savings goals: those remain in the monthly free-cash forecast. It posts nothing. Cash planning shows the dated warnings on PC and phone; Needs you links to them, with the monthly warning retained when there is no dated shortfall.

- **Items.** A bill, subscription, income or loan with an amount per payment and a schedule: frequency (once, weekly, monthly, every 3 months, yearly) every N periods from a first date, optionally ending at a last date or after N payments (loans need one). Monthly dates keep the first date's day, clamped to month end; optional `month_day` (migration 0055) preserves a chosen payday such as 31 when the first actual date is February 28. `workflows/salary_setup.py` creates an ordinary monthly income at the next payday without posting cash. **On a weekend** (`weekend_move`: keep, day before, day after, migration 0047) moves a Friday or Saturday date to Thursday or Sunday (`planning/schedule.py::on_working_day`); the default is keep, and a one-off payment always keeps its date. Last date and payment count apply to the calendar date; a reporting window applies to the moved date. A payment settled under its calendar date stays settled after the setting changes.
- **Status.** Paid (linked to a posted transaction), Skipped, Due (on or before today, unsettled) or Upcoming. Voiding the linked transaction makes it Due again. A transaction settles at most one payment. Historical loan balances recognise each posted repayment only from its transaction date (owner-approved 2026-10-14). Other recurring items use today's status; schedules and skips are not versioned.
- **Matching.** A posted, owned cash money-out (money-in for income) settles a payment automatically when it is a unique candidate for exactly one payment, on the item’s account/currency if set (profile currency otherwise). Saved per-item date and amount limits default to 7 days and 10% (1% for loans); zero means exact. Both counterparty and category must agree when both are set. Manual review (the pay popup, a transaction's page) searches every owned cash account in the item's currency and also offers early or changed payments within 45 days and 50%, never one that already settles a payment or sits nearer the previous due date; it requires explicit confirmation and never widens automatic matching. `PlanningService.early_payments` finds a next payment whose money already moved (one unlinked, same counterparty and category, in the second half of the period): the forecast leaves it out so it is not counted twice, and Needs you offers Link. Payments refuse a different currency and dates outside the schedule; loan plans use profile currency. A confirmed link stores the transaction's actual amount. A changed amount prompts but never updates later payments or a related reserve target on its own.
- **What you owe** = bills due + loans still to pay, each payment once, + Gam'eya still to pay (a savings circle's negative balance, see Gam'eya below). **Bills due** = Due bills, subscriptions and loan payments. **Net worth** = what you own − what you owe. **Free cash** = owned liquid cash − effective reserves − bills due; the Integrity check verifies free cash + reserves + bills due = owned liquid cash.
- **Loan budget lines are derived, not stored:** `BudgetService.amounts_for` asks `PlanningService.loan_payments_by_category(month)` (wired in `bootstrap.py`, so budgeting never imports planning) and plans a category with no rule of its own at that month's loan payments (not skipped). A user rule wins; `has_plan` ignores these lines. **Loan payments are spending:** recording one is an ordinary money-out in its category (default `EXP.SYSTEM.LOANS`; migration 0052 groups the ledger exceptions), so it counts in budget actuals and cash flow, leaves loans still to pay and leaves net worth unchanged. The loan is never a ledger account.
- **Instalment purchases and early payments** (`planning/loan_actions.py`, migration 0055): a purchase stores outstanding price, financed fee and count in `installment_purchases`; regular payments round up to cents and the final payment carries the exact remainder. Skips move amounts to the end without losing cents. An early payment previews a shorter schedule, then posts one ordinary loan-category outflow; `loan_extra_payments` links principal and optional settlement fee to its receipt. Principal clears overdue payments first, then future payments from the end; fees never reduce debt. Past receipts remain, partial instalments stay owed, matching uses the adjusted amount, and voiding an extra receipt restores the schedule. The automatic budget includes extra principal and fee in their cash month. Extra principal and linked top-ups also apply only from their transaction date.
- **Debt and fixed-cost ratios** (`planning/health.py`, `HealthService.at(day)`): Debt to net worth, Debt to cash, Loan payments to income, Fixed costs to income. A zero or negative divisor gives None, never a number.
- **Financial health** (`HealthService.overview(as_of)`): those ratios, the Savings rate for the last completed month, Emergency fund (same target and Settings › Budget basis), month-end Net worth for six completed months (missing = None). It calls `PositionService.at(..., match_payments=False)` so a read cannot settle a payment. Each figure has three bands (`HealthService.band(key, value)`: Good / Watch / Needs you): Good from `financial_health_good_<key>` (the old `financial_health_limit_<key>` is read as it until saved), Needs you from `financial_health_alert_<key>`; defaults Emergency fund 6 / 3 months, Savings rate 20 / 10%, Debt to net worth 30 / 70%, Fixed costs 50 / 70%, Loan payments 20 / 36%, Debt to cash none. Minimum/maximum are inclusive; unavailable figures or unset limits have no band. Emergency fund's bands are fixed (its Good is the Reserves target). Limits never edit the emergency target or financial data.
- **Cash forecast** (an estimate; changes nothing): from free cash today, per month adds scheduled income (or the three-completed-month average when none is scheduled, labelled) and separately labelled projected CD proceeds, and subtracts upcoming bill and loan payments, the budget still planned (current month: plan less spent; bills in a planned category count inside it) and what dated reserve goals still need ((target − assigned) ÷ months left). CD principal at maturity is a transfer into liquid cash, never income. **Safe to spend** = free cash − payments before the next income − budget still planned this month − Saving needed (see plan check), shown with its parts and labelled "On top of your plan until [next income]" (or for the next three months); only Budget shows a daily allowance. It never spends projected CD cash before receipt. Recurring rows sort by their earliest unpaid date, overdue first; finished schedules go last.

### Certificates and time deposits

`lightning/deposits/` models a `DEPOSIT` account as a portfolio of `DEPOSIT.CD` assets, each with principal, annual rate, start date, earliest withdrawal date, maturity (direct, or from a term in quarter-year steps), simple/compound method, payout schedule and, for compound, capitalisation frequency. The funding account must hold enough user-owned cash on the purchase date, and the service replays later cash activity so the locked-up purchase cannot make a later balance negative (earlier negative history is fine).

Interest and maturity are forecast estimates only: actual interest is entered from the bank statement, redemption records principal the user enters, and an unlinked interest entry does not settle the forecast schedule. Explicit receipt reconciliation (`deposits/receipts.py`, migration 0061) matches a dated certificate interest occurrence to existing owned bank inflows in its payout currency. Several receipts can confirm one occurrence; partial receipts leave a shortfall. Links snapshot receipt amount/date, revalidate edits and voids, and subtract only valid matched cash from that occurrence in future projections. Candidates are ranked by payer (the receipt's counterparty or alias equals the portfolio's Institution), amount (within 5%, or 15% from that bank, because a fixed monthly payout differs from day-count interest) and date (within 31 days); `match_plan` suggests at most one receipt per unmatched occurrence, one-to-one across the portfolio, closest date after the expected day first. The page pre-ticks it and offers *Match all suggested* (`confirm_suggested`: one undoable action through `confirm`, never on load). Unmatched or changed past receipts appear in Needs you as one item per certificate; a confirmed receipt within 15% of the estimate settles its occurrence there. A receipt cannot also settle a reimbursement claim (migration 0062); linking posts no cash and keeps actual investment returns unchanged. Projections use actual elapsed days ÷ 365 in `Decimal` and change no balance, Net worth or Free cash. The earliest withdrawal date is eligibility, not a cash event: before it the CD is not redeemable; from it until maturity the *if sold today* estimate applies the `DEPOSIT.CD` sale factor as an early-redemption haircut; at maturity, full principal and estimated interest. A redeemed certificate is no longer projected. Migration `0039_cd_portfolios.sql` keeps account-level `cd_terms` as legacy data and rewrites no history; old `DEPOSIT` cash must be moved out by the user.

### Gam'eya (savings circles)

Owner decision 2026-10-14: a gam'eya is built on the certificate backbone, with the interest rate optional (none by default). N members each pay the same instalment every month and one member takes the whole pot (N × instalment); an early turn borrows from the circle, a late one saves. Code: `lightning/deposits/gameya.py` (`GameyaService`), table `gameya_terms` (migration `0053_gameya.sql`, which also rebuilds `accounts` so its type list takes `GAMEYA`), page `lightning/ui/routes/gameya.py`.

- **One account per circle** (`AccountType.GAMEYA`, "Gam'eya (savings circle)", cash class `GAMEYA`, one currency). It starts empty (no opening balance; joining mid-way is recorded by entering the past instalments). Not liquid: left out of Cash you own, Free cash and Reserves.
- **Every movement is an ordinary internal transfer** (`TRF`, `Effect.INTERNAL`, never income or spending): instalment = funding account → circle, payout = circle → payout account. Balance = paid in − received; a circle's negative balance is allowed (the owned-cash rule of a CD purchase applies to the funding account, not to the circle). Instalments paid *k* and payouts received are counted from those transfers, so a voided transfer simply reopens the instalment. Interest or a fee actually received is ordinary money in or out in the circle's account.
- **Terms** (one row per circle, `GameyaTerms`): organiser (text), members 2–60, instalment, `MONTHLY` frequency (the enum leaves room for `WEEKLY`), first date (may be past), my turn (1 to members; instalment *k* falls `first_date` + *k* − 1 months, month-end clamped), payout (default members × instalment, editable for an organiser's cut), annual rate (default 0 = no interest) and the funding and payout BANK/CASH accounts in the circle's currency. Saving terms posts nothing; recorded instalments never change them.
- **Figures** (`planning/position.py`): a positive balance is **Gam'eya paid in**, a class of Holdings value with sale factor 100% (`ClassValue` fixes it; it is not a deposit); a negative balance is **Gam'eya still to pay**, in What you owe and out of What you own (`NetWorth.gameya_owed`; `NetWorth.total` stays the ledger's total for the bridge and Integrity checks, `NetWorth.what_you_own` adds the debt back). `What you owe = Bills due (other than loan payments) + Loans still to pay + Gam'eya still to pay`; never in Bills due, which would count the debt twice. Net worth does not change with an instalment or the payout. The investment report treats a circle like a deposit account (balance as value; instalments and payout cross its boundary), so it reconciles; while you owe the circle that page shows the circle below zero, where the Position moves the debt to What you owe.
- **Forecast** (estimates, nothing posts): `future_events` adds `INSTALLMENT` (negative, from the funding account), `PAYOUT` and, with a rate above zero, `INTEREST` (`DepositEvent.source == "GAMEYA"`). The interest is simple, actual days ÷ 365 in `Decimal`, on the positive balance (recorded movements plus instalments still to come) from the first movement to your turn. The forecaster keeps them apart from CD proceeds: `ForecastMonth.circle_in` and `circle_out`, in Money in and Money out; Safe to spend takes off the instalments dated before the next income ("Gam'eya instalments before next income"). Past-due items are not forecast.
- **Catch-up:** `GameyaProgress.due_indices/due_amount` derives every scheduled instalment not recorded by the as-of date; the PC and phone show that alongside any unrecorded payout, separately from the posted balance. `record_past_instalments(expected_paid=...)` posts one internal transfer per scheduled date in one database transaction; insufficient owned cash on any date rolls back the batch, and the shown paid count rejects stale/double submits. Saving terms still posts nothing.
- **Needs you:** one row per circle when the next instalment (else the payout) is past its date and not recorded (`GameyaService.attention`), naming the total due instalments and any payout due together. A circle with every instalment and its payout recorded has no events left.
- **Screens:** the circle page (PC and phone) shows paid *k* of N, the next instalment, your turn, "The circle owes you" or "You owe the circle", prefilled **Record instalment** and **Record payout**, and the terms behind **Change terms**; the account form creates the account and opens that page to enter the terms. Tests: `tests/test_gameya.py`, `tests/test_gameya_screens.py`, Mohab step 32.

`planning.emergency_context` shows free cash, money market funds accessible in days, locked certificates with their unlock date, and other holdings with access timing unknown on Reserves and Financial health. Budget limits are monthly spending constraints. Reserves assign already-owned cash to emergency or project plans; an assignment is neither a ledger transaction nor a budget limit, and reduces free cash. Budget room and free cash stay separate. Brokerage cash can be reserved, with its transfer requirement disclosed.

- **Savings waffle** (owner, 2026-10-19; Budget's moved to the Overview's Savings rate, 3Q): Investments shows total saved versus spent, without an investment split. - **Base rules:** fixed EGP, a percentage of budgeting income, or a 3/6-completed-month spending average (divided by distinct months with qualifying activity; none = unavailable, never zero, never beyond the window). The income basis is the selected owned income categories or a manual monthly amount.
- **A parent limit is a ceiling** for its branch; child amounts are allocations, never added to the cap.
- **Over a longer period** Planned and Spent cover the same months (spending counts from the first month with a plan). YTD, All time and Custom aggregate monthly base plans and actuals and include range-opening carryover once; partial-month comparisons are prorated estimates.
- **Carryover** is opt-in, default off, effective from a selected month. It is derived spending room, never cash or a liability:

```text
current_budget(M)       = base_monthly_budget(M) + incoming_carryover(M)
left(M)                 = current_budget(M) - owned_spending(M)
incoming_carryover(M+1) = left(M) when enabled; 0 when disabled or reset at M+1
```

  Positive room and overspending both carry, unclamped. A dated reset clears the incoming amount from that month and leaves history and later settings intact.
- **Everyday money** (owner, 2026-10-19). `CashForecaster.everyday(month)` returns an `EverydayBudget`: Left in plan less the plan's unpaid bills and loan payments is Budget until payday (the same figure Cash planning shows), and its day rate divides that by the days left. Everyday spending leaves out payments linked to a plan item, payments to a plan item's payee in its category, and one-off and investment categories; Budget compares it with the plan's straight-line pace and last month.
- Budget's ordinary view is a compact plan summary and a Personal/Work/Investment rollup; rule editing and background estimates open on demand.

**The plan check: one savings target for every screen** (owner request 2026-10-05). `HealthService.plan_check(month)` returns a `PlanCheck` from Average monthly income, the month's Planned (`BudgetService.plan_summary`), the Savings rate limit, Saving for goals (`CashForecaster.goal_needs` via `budgets.reserve_goal_needs`) and the Emergency fund top-up (`EmergencyFund.top_up`: the gap to six months over `EMERGENCY_TOP_UP_MONTHS`, 24). Saving needed = the larger of the Savings target and goals plus top-up; Most you can plan = income less that; `over_by` = how much to take out of the plan. Budget key notes, the line under Planned, Needs you and Financial health's Planned savings rate all read it; a longer period compares its base plan with the target alone. It replaced the separate spending-ceiling setting (migration 0042). Around it:

- *Fill this month* keeps a row ticked only while it fits Most you can plan (`HealthService.fit_fill`). Saving a bill, subscription or loan reports Fixed costs to income and, for a loan, Loan payments to income (`HealthService.commitments_note`); saving a target, goal, allocation or emergency fund says what it does to Most you can plan (`plan_note`).
- Bills and subscriptions plan their category automatically, as loans do, until it has its own rule (`BudgetService.scheduled_payments`, `bill_lines`); the forecast counts such a bill inside that plan. Needs you names a category planned below its scheduled bills (`BudgetService.below_scheduled`).

- **The smarter plan** (owner decision 2026-10-05): Safe to spend and the forecast also hold back the Rest of savings target (`ForecastMonth.target_saving`, never below zero). `HealthService.goal_reach` shows what the plan leaves for dated goals; `raise_offer` (income 5% above the average; settings `budget_income_from_recurring`, `income_raise_declined`), `short_month` and `BudgetService.over_twice` / `move_room` (over plan by at least `OVER_PLAN_MARGIN` = 50 in both of the last two completed months) feed Needs you. All of it reads the plan; only the user's choice changes a setting or a plan.

**Fill a month** (preview is read-only; it never uses actual spending or carryover as a proposal). *Last month* = the previous month's effective user-set base rules resolved to EGP there; applying creates a fixed one-month override. *Schedule* = active Bills and Subscriptions dated in the month, grouped by category (skipped payments and Loans excluded). *Goal* rows are information only (changed in Reserves). ## Persistence, precision, and indexing

- SQLite with ordered, append-only migrations; never edit an applied migration. Dates are ISO `yyyy-mm-dd`; entry accepts ISO, `dd/mm/yyyy`, `dd/m` (current year); CSV uses the same parser. An account's legacy opening date is not a transaction-date boundary; balances are chronological sums of dated lines.
- Money, prices and quantities are `Decimal` / integer `_e6`; new money inputs take two decimals. Summaries round to whole units; entry controls keep cents.
- Indexed paths: ledger account/date, asset/date, category/date, transaction id, transaction date/type/status, price history asset/date.
- Corrections are audited. Transactions are voided or deleted through recoverable flows; used categories are archived, never removed.
- **Start fresh** (Settings › Your data, `POST /settings/fresh`) never deletes data: in profile mode it locks the profile and opens new-profile setup; in browser mode it backs up, renames the database to `<name>_before-fresh_<timestamp>.db` and builds an empty one (a failed rename reopens the original).
- Data and backups live under Documents/Lightning (profiles) or `data/` (legacy), never in Git.

**Currencies and exchange rates.**

- Scheduled amounts use the selected funding account’s native currency (profile currency when unassigned). Aggregate obligations, recurring income, category funding, health and monthly forecasts convert them into profile currency using a saved rate known on the valuation date, capped at today for future dates. Missing schedule FX raises a setup error with access to exchange-rate settings; it never becomes a zero total. Transaction promotion starts at the next monthly occurrence and excludes linked certificate receipts.

- One base currency per profile (`settings.base_currency`), from the profile's registered currencies (migration 0049: ISO 4217 suggestions plus a named custom three-letter code). It can change only before ledger or FX history exists. Each account has one currency; a registered currency has one cash asset.
- `ledger_entries.amount_e6` keeps the native amount, `amount_base_e6` the dated base amount, `fx_rate_e6` the rate used; stored values are never rewritten when rates change. A foreign cash posting needs a saved rate on or before its date. `fx_rates.base` is the foreign currency, `quote` the profile currency, in profile units per foreign unit. Transfers refuse two currencies and point to *Convert*.
- **One lookup** (`lightning/fx.py::rate_for`, used by posting, valuation, reevaluation): the newest rate on or before the day, direct, else inverse (1 ÷ rate), else a cross through EGP; derived rates are rounded to 6 places and never stored. On one day MANUAL > TRADE > MARKET > ONLINE; a newer day beats an older source. Older than 10 days (`STALE_DAYS`) still values a balance with *as of <date>* (`Valuation.fx_as_of`); older than 45 (`MISSING_DAYS`) is no rate (Needs you links to type one). The `fx` price file fills MARKET rates; `workflows/live_prices.py` fetches Yahoo `<CCY>EGP=X` as ONLINE.
- **Reevaluation of foreign cash:** month-end checkpoints value native units at the dated rate and post only the rate change as a zero-quantity `VAL` journal; a missing rate stays pending.
- **Conversion** (`DocType.CNV`, `transactions/conversion.py`, `/accounts/{id}/convert`): sent, received and an optional fee in the sending currency. The receiving line arrives at the **executed rate** so internal lines net to zero in the profile currency; the fee is an OUTFLOW in Fees & Charges; amounts over 10,000 units may need their base value spread over two lines (`exact_lines`). The executed rate is saved as a TRADE rate. Create, edit, void, bulk delete and restore refresh only affected date/currency-pair keys, atomically with the posting; the highest posted transaction id wins on each day. A full rebuild remains available for repair. Spread paid = market value sent − market value received.
- **Foreign currency positions** (`reporting/fx_positions.py`, Currencies tab): average cost per currency over owned cash lines. Money in adds units at the line's profile value; money out removes units at average cost and the gap is the realized FX gain; same-currency transfers, revaluation journals and custody move no cost; a balance below zero is no position. Costs are whole cents, so unrealized + realized = held units at today's rate − the net profile value of the currency's lines (a test checks it). Per currency: Average rate, Unrealized FX gain, Realized FX gain, Spread paid.

Locked certificates keep their owned value and unlock date in a separate line beside "If you sold today" and Holdings after sale; their value is excluded from cash available by selling. Settings › Sale factors reads the same `ClassValue.after_sale` as Position, including per-certificate lock-ups and factors, rather than multiplying a class total by a generic factor.

### Action history and checked accounts

`undo.py` installs connection-local TEMP row journals/triggers after startup. A UI action context groups its nested service transactions and autocommit metadata writes; explicit `Database.transaction(undo_label=...)` supports other workflows. Twenty undo/redo groups are retained. Replay is one immediate transaction, verifies the current history head and affected row snapshots, handles recorded cascades, defers/checks foreign keys and validates changed ledger postings/holdings and checked balances. Audit records are append-only and not replayed. Startup, background price work and reads have no action context. History is never copied into backups or phone hand-offs, and expires with the connection/profile session; changed dependencies can make replay refuse safely. Successful UI writes settle unambiguous planned-payment links under the same action context. Existing scoped bulk-undo controls remain compatible.

## UI contract

## CSV import and export contract

**SMS currency:** the current CIB/NBE patterns read EGP only. Assignment and saved mappings accept EGP accounts; foreign or inactive mappings leave messages waiting for reassignment, and withdrawal suggestions use an EGP wallet (`sms_imports.py`). CSV statements use the target account’s native currency and dated FX rates.

Import normalises one signed amount column or separate inflow/outflow columns into one signed amount (money out negative) before review. Rows stay unposted until reviewed. Review is one editable row per statement line (`counterparty_<id>`, `category_<id>`, `whom_<id>`, ...), grouped by imported name only for display; a bulk bar writes values into ticked rows. **Same-day order:** `confirm` posts a day's inflows before its outflows when the account balance at the end of that day is at or above zero, and keeps statement order when it ends below zero (account balance only, not per held-for owner). A statement left in review can be discarded (`BankImportService.discard`; nothing posted is touched) and Import CSV shows a waiting review first (`BankImportService.waiting`). The AI preparation helper builds CSV instructions locally and contacts no provider.

**Matching rows you already recorded.** Same-account, exact signed native-cash amounts within three days remain the import candidate boundary. Migration 0057 allows multiple source batches to support one transaction, with one row per transaction/account within a batch. Review shows source filenames/counts. Multiple candidates and already-supported entries require an explicit choice; only one unbacked candidate may default to Link. Exact bank references still detect duplicates, repeat uploads default to skip, and linking never reposts money. Imports skip new postings dated within protected checked history; explicit provenance links remain possible because they do not change the ledger. Ordinary cash duplicates have a fingerprinted merge preview: matching accounts/assets/quantities/effects, dates within seven days, bank-reference entry retained, blank metadata/category and missing tags preserved, safe plan/reserve/source links moved, duplicate voided. Conflicting or unsupported dependencies and checked history require resolution first. Voiding removes the duplicate's cash effect once; it does change the balance.

**Bank column presets:** confirmed column mappings are reused for the exact header signature on the same account, then across accounts with the same nonblank institution name (case-insensitive). Conflicting saved interpretations require a manual choice. No bank layout is guessed. Uploads are bounded to 5,000,000 bytes, labelled 5 MB; PDF/Excel parsing remains future work.

**Export all data** (`workflows/data_export.py`, Settings › Your data): one consistent read snapshot of an explicit financial-table whitelist, including archives, voids, plans, unfinished imports and audit history; credentials and runtime/device configuration are excluded. IDs and dates remain, millionths become decimal values. CSV is a UTF-8 ZIP with formula-looking text escaped; Excel uses inline strings and splits sheets at its row limit, rejecting oversized cells instead of truncating. Files are built in memory, unencrypted inspection files, not restorable backups.

**Selected CSV exports** (register, Categories, reevaluation ledger) take explicit IDs, at most 1,000, never a whole account. A transaction export has one row per ledger line with transaction and line IDs, account, asset, category, quantity, amount, base amount and owner ID. They are inspection files, not the import format; text starting like a formula is prefixed with an apostrophe.

**Export for AI** (Settings › Your data): one in-memory `.xlsx` (Summary, Transactions, Investment ledger, Categories) for All time, YTD, Monthly or Custom (`ui.periods.parse_period`), built by `AIAnalysisService` (`workflows/ai_analysis.py`). It holds every posted owned line in the period without the export cap; a line owned by another person is omitted, a categorised expense paid externally for the user stays. Strings are OOXML inline text, so content cannot become a formula. Nothing is sent to an AI provider and no plaintext temp file is written.

## Desktop app and encrypted profiles

**State:** v1.1.0-beta.1 (`lightning/__init__.py`), unsigned. Use dummy data until ordinary-PC acceptance, legacy import and backup restore are done (see Open before a beta).

**Shape.** FastAPI, Jinja and every financial service are shared. Windows: `Lightning.exe`, a thin pywebview 6.2.1 + WebView2 shell (`lightning/desktop/`) in a PyInstaller one-folder ZIP (needs the WebView2 Runtime, not Python). Linux: `python -m lightning --profiles` runs the same runtime in a browser. `lightning.runtime` (paths, instance lock, session, HTTP guards, launcher) sits between `lightning.desktop | lightning.main` and `lightning.ui`; `lightning.security` beside `lightning.database`. Browser mode never imports pywebview, pythonnet, WinForms or winreg.

**Profiles and data.** Container `Documents/Lightning/` (Windows known-folder API; Linux `XDG_DOCUMENTS_DIR`, else `~/Documents`).

- **Layout** (`runtime/paths.py`): one folder per profile, `Name_YYYY-MM-DD_NNN_<id>/`, holding `<same>.db`, `keys.json`, `instance.lock`, `backups/`. A chosen database keeps its companions in `.<name>.db.lightning/`. Backups append `_backup_<date>_<seq>_<id>`; pre-upgrade copies `_upgrade_`.
- **Discovery** scans only the container or a chosen folder, lists profiles and backups apart, never opens the newest-looking file. Alternate locations are typed paths (no native picker yet). A plaintext legacy database, a backup chosen as live, or a hardlinked path is refused.
- **Sync folders:** a local lock cannot coordinate two PCs. Never open one live database on two computers; move completed encrypted backups.

**Encryption** (`lightning/security/keys.py`, `runtime/session.py`).

- **Engine:** SQLCipher via `sqlcipher3` 0.6.2, keyed with a raw 32-byte data key made once per profile and never typed. Database and backups use only this key; `key_id` (an HMAC of it) is not secret.
- **Three secrets** (owner decision 2026-10-05): a password of any length (setup suggests four BIP-39 words and advises without blocking); a 12-digit recovery key (`1234-5678-9012`, shown once and confirmed with a press, not retyped: owner 2026-10-06); a security question whose answer ignores case, spaces, punctuation, Arabic letter variants and digit script.
- **`keys.json` v2** holds two locks on the data key, each AES-256-GCM under an Argon2id key: the password (128 MiB, 4 passes) and recovery key plus answer together (256 MiB, 8 passes). A copy in `backups/keys.json` is read when `keys.json` is missing or damaged.
- **One thing opens, two things change.** The password opens; recovery key plus answer set a new password. While open, being open counts as the password: a new password needs the answer or the recovery key, a new question needs the recovery key, a new recovery key needs the answer (replacing the old only once confirmed). Any two restore the third; losing the password and another loses the data. A change rewraps the same data key; nothing is re-encrypted.
- **Wrong tries** (`AttemptGuard`, `attempts.json`): five free, then waits of 1, 5, 15 minutes and 1 hour; never a permanent lockout.
- **Fingerprint slot** (phone only, opt-in, owner 2026-10-14; `security/biometric.py`, `android/.../BiometricBridge.java`): a third wrapping of the same data key under an Android Keystore AES-256-GCM key that needs a strong biometric for every use (`BiometricPrompt` with a `CryptoObject`, API 30+, invalidated when fingerprints change). The wrapped copy is `appdata/biometric/<profile id>.json` (`key_id`, iv, ciphertext), outside the profile folder, so `keys.json` and the PC are untouched and the raw key is never on disk. Unlock goes through `ProfileSession.unlock_with_key`, the password road after its password step; it checks `key_id` against `keys.json` first and, on a mismatch or an invalidated key, deletes the slot and the Keystore key. Android counts fingerprint failures, `AttemptGuard` none. On needs the open profile, the password typed again and the prompt; off deletes both; a password change keeps it valid (same data key); lock and idle lock work as before and keep no key.
- **Same scheme on Windows and Linux** (owner decision): nothing is tied to hardware or a Windows account. Not in v1: changing the data key or rewriting backups.
- **Threat model:** a copied database or backup without `keys.json` is a 256-bit problem. With `keys.json` someone can guess offline at either lock (Argon2 slows each guess). Nothing protects an unlocked PC from malware.
- **Freed memory is not wiped** (`PRAGMA cipher_memory_security = OFF`, `database/connection.py`, owner decision 2026-10-03; wiping made encrypted reads about 3× slower). SQLCipher still wipes key material; decrypted fragments may persist in freed memory, crash dumps, the page file or hibernation file. The setting is process-wide and cannot be turned back on, so nothing else may turn it on.

**Lifecycle and the database thread.**

- **One thread:** connections are opened, migrated and closed only on the ASGI runtime's owning thread; the GUI sends commands, workers only return data. The socket is bound and the instance lock taken before any database work.
- **Lock, switch, shutdown** stop new operations, invalidate the session generation, drain requests, close connections, wipe keys, release the lock last. Finance writes carry the generation token, so a stale tab cannot save into another profile. Idle lock: 15 minutes of foreground activity.
- **Session roles** (`runtime/roles.py`): *home* (writable), *borrower* (a PC's working copy) or *reader*. A reader opens a real read-only SQLite connection (`build(read_only=True)`: no backup, migration, seed or payment matching; a copy needing upgrade is refused); the request gate only explains "This is a read-only copy". `SessionGate.change_role` reopens the profile in another role between requests, with no password. A borrowed profile lives in `<local app data>/Lightning/borrowed/<profile_id>/`, never in Documents or a synced folder.
- **Migrations** commit each script and its version row together. A missing migration resource or newer-schema database stops the app before any write. Before a pending migration a verified pre-upgrade encrypted backup is written and kept outside pruning; if it fails the migration aborts. Backups are encrypted snapshots reopened to check integrity, foreign keys, schema, rows and sequences.

**Restore and promotion** (`runtime/restore.py`, `database/promotion.py`, `promotion_windows.py`; `tests/test_database_promotion.py`). The locked chooser links each backup to a password and confirmation screen. Restore accepts only a backup of that named profile, keeps the selected bytes and a verified pre-restore snapshot, migrates a private candidate, records a hash manifest before P1 and publishes through P0–P5 under the instance lock, leaving the session locked; unlock compares manifest, journal and retained hashes. It refuses ambiguous sync control, unresolved evidence, SQLite sidecars and missing retained files. A password-gated repair screen can resume one matching P1–P4 journal to P5; there is no automatic rollback. Legacy import is not built.

**Promotion durability risk and release gate.** The journal and hashes stop an uncertain state opening for writes, but they rely on the OS and device honouring completed flushes (POSIX fsync of file and directory; Windows `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`, which has no parent-directory equivalent). A sudden power loss may lose or reorder writes and recovery may need an older backup. Tests cover injected disk and flush failures, process kills at each durable phase and one real SQLCipher restore per adapter; they are not power-loss evidence. Before accepting restore for real data, run it with dummy encrypted data on an ordinary Windows PC: interrupt at the phase boundaries, restart, confirm unlock reaches the verified checkpoint or stays locked with evidence intact and no write path; record device, filesystem, method, phase and outcome, and report a normal reboot or process kill apart from an abrupt power cut. Without a real power-cut drill, label this **unverified** and require an explicit release-risk decision by the owner.

**Multiple devices** (built 2026-10-06, milestone 1; plan and unbuilt tasks: [4B](../issues/4-edit-journal-and-devices/4B-multiple-devices.md); `tests/test_two_devices.py` walks the journey). The phone is the ledger's *home*; a paired PC *borrows*, edits and hands back; one writes at a time. Code: `sync/` (`domain.py` protocol, v1 frozen in `tests/fixtures/sync_v1.json`; `state.py` state machines; `control.py` a FULL-synchronous control store per profile per device, outside the profile folder, where a missing or damaged record blocks writes and never resets to "at home"; `service.py` lend and hand back; `identity.py`, `transport.py` the link) and `runtime/devices.py`.

**Experimental edit journal** (`sync/journal/`, `ui/journal.py`, `ui/journal_views/`; tests: `test_edit_journal.py`, `test_journal_finance.py`). The owner authorized J1–J6 in [the design](../issues/4-edit-journal-and-devices/4A-edit-journal.md); the current engineering slice covers base-currency bank/cash transactions in explicit encrypted dummy profiles. Production profiles still use v1. A database carrying any `journal_*` table cannot open through the ordinary launcher, even read-only; an explicitly opted-in journal runtime refuses pending ledger migrations and skips seed, ownership repair and legacy undo startup writes. No live profile conversion or production pairing is exposed.

The core persists immutable signed v2 proposals and their origin counter atomically with FULL synchronous writes. Inbox, strict per-origin progress, financial rows, field-group tokens, terminal receipts, source identities and signed commit chain share one database. Encrypted form drafts retain the values and field tokens actually displayed; a later sync cannot refresh a stale form’s preconditions, and retrying one form submission reuses its saved identity. A separate idempotent review lane cannot deadlock its origin. Dependencies are earlier edits from that origin; aliases resolve dependent references. `CashAdapter` calls the normal transaction services for add/edit/void, transfers and expense splits; effects are generic exact rows (`sync/journal/effects.py`, schema 2): the home's temporary triggers record each touched row of the synchronized tables (today `transactions`, `ledger_entries`, `counterparties`), and the commit carries their final values with references as UUIDs, or a delete. Row identity is a UUID from `journal_ids` for integer `id` keys, otherwise the key columns with references mapped. Every replica, including the dummy lab and tests, starts from the home's verified checkpoint (`snapshots.checkpoint_replica`); `initialize` creates homes only. Replicas check every row against their own table schema and apply deletes children-first and upserts parents-first, then check postings, without rerunning saves, categorization or automatic matching. Writes to any other table are refused; `reserve_transaction_links` may only be cleared as a no-op. UUID mappings survive different physical row IDs. Fingerprints combine per-row hashes of synchronized rows (UUID identity and references, exact integers) as a sum mod 2^256, excluding wall-clock columns, physical IDs, outboxes, caches and audit/history tables. Effects and the cached hashes (`journal_fp`) cover only touched rows; a replica reads each applied row back and refuses a commit whose rows differ, and after every catch-up recomputes every row against the cache (`store.verify`), as do checkpoints, repair and enrollment; a mismatch asks for a verified snapshot. Baseline catalog compatibility is separately hashed. Changed group preconditions wait for home review; normal financial validation rolls back effects before recording a refusal. Any other error from one proposal parks it in review (`home-error`) so other origins keep confirming; storage failures still stop the run. Signed commits double as receipts: a home that took over answers a resent prefix proposal with its original decision and resumes each origin after its last decided sequence. Fuzzy duplicate review applies only when a captured payment (with a source) is involved. All canonical writes outside confirmation/replay are denied by the connection authorizer; resetting it invalidates previously prepared statements. Unsupported areas have no experimental UI routes. Reclassification, foreign currency, investments, bills/loans/reserves, master-data edits and financial automation remain disabled.

**Command proposals (J6c).** Areas beyond the cash register travel as commands (`sync/journal/commands.py`, `areas/`): kind `command.<service>.<action>` names an allowlisted service method with typed arguments (text, date, amount, flag, choice, UUID reference). Each area module lists its synchronized tables and commands; `effects.SYNCED` is their union, so a service writing any other table is refused. A command on an existing record carries the hash of that row and every row it owns (foreign keys with `ON DELETE CASCADE`: a transaction's ledger lines, a rule's conditions) as its precondition; a bulk command (`targets`) carries one hash over every selected record. A changed record waits for home review, and a device's own earlier pending command is its base instead. A command that changes a transaction removes it from the register's field groups (`journal_records`), so a register edit cannot revert it; the register refuses to edit it. The home maps UUIDs to local ids, calls the service inside confirmation and publishes the touched rows; a create command binds the new row to the proposal's record UUID. Pending commands are listed on the device (`pending_commands`), never drawn as register rows; confirmed data changes only by the exact effects. Areas (`areas/*.py`): cash register, master data (accounts of every type, categories), currency (currencies, rates, conversions, reserves), plans (bills, loans, instalments, budgets, carryover), people (aliases, money held for others), settings (every key is profile-wide), investments (trades, dividends, fees, moves, pockets, prices, targets, revaluation), deposits (CDs, gam'eya) and physical items. Every table these touch is synchronized; effects carry REAL columns as exact shortest-float text, and a command that changes nothing is accepted with no rows. `python tools/journal_coverage.py` lists each POST route as covered, partial, uncovered or read-only (2026-10-16: 77 covered, 14 partial, 40 uncovered, 18 read-only of 149); `--check` guards the covered list. An uncovered write on a journal profile returns to the page with "This is not available on a synchronized profile yet." `python tools/journal_mohab.py` lives Mohab's year on a journal home and prints the first gap: today bank-statement import. An action too large to carry inline (more than 64 rows or 40 KiB) is published as a manifest of 24 KiB chunks (`journal_chunks`, at most 44, about 1 MiB); a replica applies the commit only once every chunk is present and its hash matches, fetching missing chunks four per sync round (`pieces`).

**The app's own screens on a journal profile (J6f).** `proxy.JournalServices` wraps the container the routes use: reads go to the confirmed copy; a covered service call becomes a command. On the home it is confirmed at once and the route gets the service's own result or refusal; on another device the action is first rehearsed against the local copy and rolled back (a refusal shows at once, in the service's words), then saved, and `PendingOnHome` sends the screen back with "Saved on this device. It takes effect when the home confirms it." Uncovered writes still reach the connection guard and are refused. `python -m lightning.runtime.journal_lab --dummy --root DIR --app` opens the app's own screens for the dummy home and PC (a saved change on the PC syncs at once). Not yet: the production profile picker on a journal profile, refusal and review display for commands, and per-route coverage of composite actions.

`JournalDevice` builds disposable pending overlays; balances read only confirmed postings. Pending deletes retain the confirmed value. Refusals are shown as Not taken; an IntersectionObserver acknowledges actual visible display, and the device hides a refusal one week after its first durable display acknowledgement. Add again and undo allocate fresh proposals; undo sends only the groups the undone action changed, checked against that action's result tokens, so a later change on any device goes to review. Detailed decisions, compact identity/source metadata, aliases and tombstones are conservatively retained; pruning/compaction is not enabled. Signed encrypted checkpoints use the existing verified snapshot exporter, remove the sender's local queues/transport secret, and repair a replica's domain/protocol state in one transaction while preserving its identity/counter, outbox, local capture and unseen decisions. Repair checks authority, schema, catalog, file hash and fingerprint, refuses revision rollback, and retains an encrypted pre-repair comparison copy.

`LocalChannel` authenticates recipient/profile/generation/key-epoch routing and outer signatures before AES-GCM decryption, checks current origin membership, and binds replies to the request nonce. Inner proposals retain their signatures. `PinnedLocalClient` uses TLS 1.3 with only the paired certificate trusted and bounded request/response bodies. Incremental catch-up is one combined `round` request: capabilities, up to 50 unsent proposals (36 KiB), their statuses and the cursor; the reply carries as many contiguous signed commits as fit 40 KiB. When the home holds an upload (staging limit) the device still applies the downloaded commits, then reports `UploadHeld`; the edits stay pending. 20 offline edits converge over the mailbox in 3 wake cycles (measured, `tests/test_journal_transport.py`). The experimental UI has separate PC and phone frames; the phone uses separate register, entry, capture, review and balance pages. Cookie/Origin/form-token guards protect the UI; protocol errors never render the home UI or session token. Multipart uploads are bounded and kept in memory. Foreground view refresh preserves unsaved forms; saves/app-open coalesce catch-up without waiting for networking. These English engineering screens and injected peer/SMS adapters still need native/Arabic acceptance and production enrollment.

`JournalCapture` uses the existing SMS parser and CSV normalization to stage encrypted local candidates, never postings. SMS cursor advancement and candidates commit together; cursors are per account and configured card endings are checked. Candidates can be corrected, split or identified as transfers before any proposal is saved. Each reviewed payment gets one proposal; retries reuse that candidate's proposal. Namespaced source IDs preserve validated equivalence across SMS/CSV linking, and conflicting reused source IDs cannot post a second payment. Merely similar payments wait on the home for link/post-separately/refuse. Imports expose progress and idempotent per-payment undo; linking an existing payment never makes that payment part of the import's undo. Rules, price fills, bill matching and other automatic financial work remain disabled in journal profiles rather than writing outside the journal.

Run `python -m lightning.runtime.journal_lab --dummy --root /path/to/empty/journal-lab` for password-protected persistent dummy home/PC windows and actual pinned local TLS exchange. The UI stays on loopback; a separate pinned TLS protocol listener and bounded UDP discovery responder accept local-network peers. The launcher holds an instance lock, keeps unwrapped profile and transport keys only while open, uses single-use 30-second launch codes without access logging, and retries the local link every 30 seconds while open. Forgotten dummy passwords have no recovery flow. This is separate from the production profile picker and Android enrollment. `python tools/measure_journal.py --edits 30 --report /tmp/journal-cash.json` measures application bytes against the encrypted whole-file baseline (2026-10-16, 30 cash edits on a fresh profile: 7,952 bytes and one round per edit against an 847,872-byte file); it excludes TLS/IP overhead, Android timing and internet billing. The older `python -m lightning.sync.journal` remains a dummy-record simulator. Test evidence includes encrypted restart, true process exits, disk-full failures, exact replay with different local IDs, real pinned TLS, independent seeded-model checks and Chromium PC/phone journeys; none establishes physical power-loss durability.

**Experimental cloud and local routing.** `runtime/journal_routes.py` tries saved private-network endpoints using the paired TLS certificate, then authenticated IPv4 UDP discovery (`sync/journal/discovery.py`), then an optional `JournalInternet` runtime. Normal discovery binds the current transport-key epoch; a signed control locator lets a still-approved device find an address before fetching a missed key rotation. Both bind profile/generation, recipient and a fresh challenge; the TLS connection verifies the saved certificate again. Revoked devices receive neither locator replies nor key updates. A successful bounded local round keeps its durable cursor and does not use cloud. Network failure triggers fallback; financial/compatibility refusals remain visible. The experimental Devices screen discovers named nearby homes only during an explicit ten-minute pairing window, proves the six-digit code, shows matching digits on both screens, and only after the joining device's user confirms them sends a profile-password proof (Argon2id-keyed HMAC over the offer and request) over TLS pinned to the offered home key. The home admits the device only with its own digit confirmation and a valid proof; code and proof each allow three attempts. No address or port is typed. It currently admits compatible dummy replicas; first-profile checkpoint enrollment remains a native integration gate. Signed membership updates rotate transport keys and reach existing devices automatically over LAN or the mailbox. Saved pairing keys authenticate routine sync without new user prompts. IPv6-only discovery, native network permission/lifecycle behavior and real two-device enrollment still need integration/acceptance.

`cloudflare/journal/worker.mjs` is an opaque carrier and authority-registry prototype, tested in Miniflare/workerd without an R2 binding. Deployment permits Workers Free and SQLite Durable Objects only. Signed HTTP requests bind method/path/body hash, generation, time and single-use nonce. Per-device request/byte limits, per-sender/recipient queues and separate control capacity bound staged work; the profile's mail payload is capped at 128 MiB. Snapshot reservations total at most 400 MiB per profile, each checkpoint at most 200 MiB. Immutable 32 KiB encrypted chunks and their digests commit together in SQLite, with small digest indexes for resumption. Queues expire after 30 days and snapshots after seven; expiry preserves registry/retirement records and stops scheduling alarms when no delivery cleanup remains. Hibernating sockets send only wake hints. Optional FCM HTTP v1 hints use a Worker service-account secret; no native FCM receiver is integrated yet.

`cloud.py` persists encrypted local requests, deliveries and replies before mailbox acknowledgements. Retrying an offline RPC reuses its sealed request; consumed empty replies cannot hide later commits. `CheckpointTransfer` verifies the signed manifest first, resumes hashed ciphertext chunks, fsyncs cache writes and checks the complete file hash before repair. Capabilities precede proposal upload; incompatible schemas/kinds retain queues and identify which peer needs updating. Wake-ups have request/time budgets and backoff; a request queued for a reply that has not arrived (`ReplyPending`) waits 30 seconds without counting as a failure. An envelope the device refuses is recorded (`processed=2`) and acknowledged so it cannot block later mail; a request the home authenticated but could not take (frozen, staging full) is answered `refused`, so the device retries with a fresh request (`HomeRefused`). The worker keeps each wire under its own key and lists 64 small entries per receive. Each profile has a monthly allowance (UTC month): `MONTHLY_REQUESTS` sync calls (default 1,500), `MONTHLY_SNAPSHOT_REQUESTS` checkpoint calls (default 4,000) and 200 registry/membership calls; over it the worker answers 429, edits stay on the device and the local link still works. `deploy_free.py` checks the account's subscription inventory and a strict configuration allowlist before deployment; unverified, trial, metered or paid plans block it. It never changes subscriptions and supplies no automatic upgrade confirmation. Account changes made outside this deployment path remain an operator responsibility. Cloud configuration and actual provider quota/CPU/row-usage evidence remain pending.

**Experimental trust and backup primitives.** `owner.py` creates an independent P-256 authority credential, using existing Argon2id/AES-GCM locks under each pair of owner secrets. It does not change the profile data-key recovery scheme. This construction and individual ECDH transport-key wraps require independent security review before production. `pairing.py` verifies the code and password-derived transcript proof, signatures and matching six digits before home approval; attempts/expiry and temporary proof state live inside the encrypted profile. `membership.py` publishes signed membership epochs and wraps a fresh random transport secret separately for surviving devices; revoked incarnations cannot be revived or derive the next secret from the old group/data key.

`authority.py` keeps generation memory outside profile backups. Confirmation holds its control lock through each financial commit so a freeze/retirement serializes with writes. Missing control metadata blocks an enrolled home. A cooperative move verifies the final checkpoint and target preparation, copies the final inbox/receipts, durably retires the old home, then activates the target. Recovery requires live registry CAS publication and checking its winning owner-signed certificate; known retirement blocks old-home confirmation and permits revalidation of admitted original signed proposals. Freeze, preparation and retirement retries preserve their original signed receipts. Activation resumes after the independent control commit or the encrypted profile commit; its transport reset and financial authority configuration commit together, and retry reuses the new secret. Retirement verification binds the pinned old home key. The carrier retains paged owner-signed authority certificates; offline peers verify each link, including owner-key changes, and durably fence the valid prefix before requesting repair. Owner-credential rotation UI and complete native lifecycle integration remain open. `backups.py` creates device-signed encrypted local packages containing the outbox and identity/wrapped-key material; queue recovery preserves the current ledger, counters and decisions, imports original identities atomically and keeps comparison evidence. It does not reinstall an old incarnation or rewind a live home. J6 coverage and cutover remain blocked; ordinary profiles continue using v1.

`runtime/journal_enrollment.py` and `sync/journal/enrollment.py` implement first-replica enrollment after numeric approval, without requiring a pre-created compatible database. The approved device signs bounded metadata/chunk requests over pinned TLS. Immutable ciphertext chunks resume from verified cache; full-file hash, SQLCipher integrity, schema, catalog, financial fingerprint and cursor are verified before exclusive publication. A durable install intent resumes a stopped publication without network access or another pairing code. The new database starts with its own incarnation and counter, contains no sender-local queues/private identity, and receives its individually wrapped transport key. Enrolled homes must also supply the wrapped owner credential and complete authority chain; generation memory is installed outside the new profile directory. The source cache is bounded at 400 MiB. These runtime services are tested; the ordinary native profile picker has not been switched to them.

- **Lend and hand back:** the home checkpoints (unlocked only), refuses a borrow when the live fingerprint differs from the checkpoint, and reopens read-only before granting. A returned copy is verified (integrity, schema, `profile_identity`) and promoted when the phone is unlocked; the old copy stays as `<name>.before-<return id>.db` (last three kept); a failed check leaves NEEDS_REPAIR with every file kept. A PC's copy is writable only while BORROWING; lock, idle lock and closing hand back when the phone answers within 5 s, else seal. Moving a home is two-phase so a lost message never leaves two writable copies. A profile set up for lending carries `lending.json`; without its device record it opens read-only and offers *Keep this copy*. Restore is refused while lent or mid hand-back.
- **Link:** the phone listens on port 47513 with TLS 1.3; each device has an ECDSA P-256 key and self-signed certificate. Pairing uses a one-time 12-character code (ten minutes; three wrong codes per address) proved by HMAC bound to the certificate, with six check digits on both screens. The phone sends the profile's locked key file, so the PC uses the same password (owner, 2026-10-06: one password per profile); the PC then pins the certificate and signs every challenge.
- **Not built:** prefetch while the password is typed, periodic recovery copies, discovery (the PC types the address), resumable transfer, comparing copies on take-back, the two-PC fault gate, power-loss evidence.

**Local server security** (`lightning/runtime/http.py`). Loopback only, random port; Host and Origin must match exactly. A single-use launch code (30 seconds) is exchanged for a per-instance HttpOnly, SameSite cookie required on every request. `no-store` responses, a nonce-based script CSP, no inline event attributes, `Referrer-Policy: same-origin` (`no-referrer` would turn same-origin POSTs into `Origin: null`). POSTs are capped at 512 KiB (`MAX_BODY`); the CSV import route takes up to 5 MiB, with the multipart spool threshold raised so CSV bytes stay in memory, never plaintext temp files (verify this if limits change). PDFs are not accepted. No outside requests; logs hold no query strings, form values, amounts, names, tokens or keys.

**Window** (`lightning/desktop/window.py`). `edgechromium` is required (no IE fallback); a native navigation guard is attached before any page loads, and startup fails visibly if it cannot be. Blocked: foreign origins, unexpected schemes, new windows, file drops. No `js_api`, no remote debugging port. pywebview's `storage_path` never points at user data (6.2.1 deletes it on exit in private mode). A repeat launch focuses the locked profile's window.

**Build and release.** Actions minutes are limited and Windows counts double (owner, 2026-10-06), so nothing is built or tested twice. The rules for what each push, daily, manual and tag run does are in `packaging/ci_scope.py` and `.github/workflows/desktop-probe.yml` ("PC and phone app") and `android-app.yml` ("Phone app").

- **The ZIP that ships is the ZIP that was tested.** `packaging/package_app.py --strict` packages the PyInstaller build (README, `BUILD_INFO.txt`, licence notices in `packaging/notices/`, `Lightning.exe.config`, price packs; it refuses any database, key, log, profile or backup) and writes `APP_SHA256SUMS`. CI checks the ZIP against it, extracts it fresh, marks it downloaded and requires `--self-check` and `--smoke` to pass through `packaging/run_check.ps1` before upload.
- **Names:** only a tag matching the source version makes `Lightning-v<version>-Windows-x64.zip`; any other build is `…-dev-r<run>-<commit>-…`.
- **Matched test builds** (owner, 2026-10-07: the owner reviews milestones with one PC and one phone build of one commit): a manual run on `main` gives `Lightning-Test-<version>-<count>-<commit8>-PC` and `…-Phone` (`packaging/phone_build.py bundle`), seven-day downloads, never a release.
- **Phone test app:** CI builds **Lightning Test** (`org.lightning.app.test`, `versionCode` = commits on `main`, name `<version>-test.<count>+<commit8>`); local builds stay `org.lightning.app` for Google Play. Python packages come only from `requirements/android.lock` (`tools/android_lock.py`). `phone_build.py check` fails an APK that breaks the lock or `packaging/android-permissions.txt`, or holds a database, key, backup or log. A second job, the only place the test key exists, signs it.
- **Beta signing key:** repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`; its fingerprint is pinned in `packaging/android-test-certificate.sha256` and a missing secret or mismatch fails rather than sign with another key (Android updates only same ID, certificate and non-falling `versionCode`; losing the key means one uninstall). Google Play needs an App Bundle under `org.lightning.app`; this APK cannot be promised to update a Play install.
- **Releasing a version:** bump `lightning/__init__.py` and `pyproject.toml`, add the changelog entry, push to `main`; tag that commit (`git tag v1.1.0-beta.1 <commit>`, push the tag). CI refuses a tag differing from `v<DISPLAY_VERSION>` or not on `main`; after the Windows and signed phone jobs pass, the release job publishes both tested files to `elfekimuhammed/Lightning-downloads` (prerelease for a beta). It never replaces a release or tag and publishes a draft only after reading its uploads back byte for byte (`tests/test_release_publish.py`). Then add the version to the website's archive by hand; earlier entries stay.
- **One-time setup (owner):** a fine-grained token limited to `Lightning-downloads` (Contents: read and write) as Actions secret `LIGHTNING_DOWNLOADS_TOKEN`, and release immutability on in that repository.
- **Distribution:** unsigned. An Actions artifact needs a GitHub sign-in and expires after seven days; it is a CI handoff, not hosting. Owner decision (2026-10-03): keep at least the three latest versioned downloads permanently, each an immutable asset with its own website entry; delete a version only if the owner decides. Never make disabling Windows protections part of installation. Signing becomes necessary if recipients' PCs refuse the build.
- **Updating:** close the app, extract the new ZIP into a fresh folder, launch. Data stays in Documents. An old build refuses a newer schema; rolling back needs the matching pre-upgrade backup.
- **Developer checks:** `python desktop_app.py --self-check --report result.json` uses disposable data; on Windows `--smoke` checks the real chooser. `packaging/check_profile_browser.cjs` drives Chromium and Firefox through setup, saves, cross-tab lock, reopen, mobile layout and CSP.

**Open before a beta.** Legacy import and safe promotion of a backup restore; native file pickers; a clean-machine pass on ordinary PCs, including the second PC that failed at window startup; ZIP update acceptance from N to N+1; Windows and Linux acceptance runs.

## Working rules

1. Check `git status` first; preserve existing user changes and personal data.
2. Define a new concept in the Glossary before building it.
3. Persistent state needs a new migration and a module that owns its table. Never rewrite an applied migration.
4. Cross-module actions go in a workflow or service, with all writes in one database transaction.
5. Post every main-ledger effect through `TransactionService`. Generated valuation journals use `source=SYSTEM` and stable links to their reevaluation details.
6. Keep the UI thin (see UI contract).
7. Test the changed workflow and its invariants (date and money edge cases, ownership and net-worth effects, posting, archive, void). Run the full pytest suite, the import-boundary checks and `git diff --check`. Keep meaningful business assertions when updating old tests.
8. For UI changes check populated and empty data and a 390px viewport, and re-run Mohab (`tests/test_mohab_year.py`) when a workflow changes.
9. Log changes under `Unreleased` in `CHANGELOG.md`; keep the files in AGENTS.md section 1 consistent, and add no new files under `docs/`.
